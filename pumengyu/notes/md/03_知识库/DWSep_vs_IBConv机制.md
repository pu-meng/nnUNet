# DWSep vs IBConv 机制

## 朴素 DWSep 替换 vs 倒置瓶颈（IBConv）：问题所在与正确做法


#### 朴素 DWSep 替换 vs 倒置瓶颈（IBConv）：问题所在与正确做法

##### 背景

目标：在 MLAUNet 的 Encoder + Decoder 中用**深度可分离卷积**替换标准卷积，
以更低的参数量支持更大的感受野（k=7 vs k=3）。

---

##### 方案 A：朴素替换（`MLAUNetDWBot3D`）

```
原始 ConvDropoutNormReLU:
    Conv3d(C_in, C_out, k, stride=s) → InstanceNorm → LeakyReLU

替换后（_replace_encoder_conv3d_with_dw_sep）:
    DW: Conv3d(C_in, C_in, k, stride=s, groups=C_in)   ← 大核 + 可能有 stride=2
    PW: Conv3d(C_in, C_out, 1, stride=1)
```

###### 核心问题

**大核步长卷积触发 cuDNN 最慢路径**

cuDNN 对 Conv3d 有三条主要路径，底层数学完全不同：

| 路径 | 适用条件 | 速度 |
|------|----------|------|
| Winograd | k=3, stride=1, 非 depthwise | 最快（~3× 提速）|
| FFT | 大核, stride=1, 非 depthwise | 快 |
| implicit GEMM | 通用 fallback | 基准 |
| **grouped large-kernel strided** | k≥5, stride≥2, groups=C | **极慢（无任何优化）** |

###### Winograd 数学原理

**核心思想：相邻滑动窗口有大量重叠，合并重复计算。**

1D 输入序列（d 是输入数据，g 是卷积核权重），k=3 stride=1 时两个相邻输出：
```
输入:  d₀  d₁  d₂  d₃

y₀ = d₀·g₀ + d₁·g₁ + d₂·g₂    ← 窗口 [d₀, d₁, d₂]
y₁ = d₁·g₀ + d₂·g₁ + d₃·g₂    ← 窗口 [d₁, d₂, d₃]，右移一格
```
两个窗口共享了 d₁、d₂ 两个元素（重叠 k-1=2 个）。
正是这种重叠，让我们可以把公共项提取出来，用 4 次乘法代替 6 次：

```
步骤 1  把 kernel 变换到 Winograd 域（权重固定，只算一次）：
    G₀ = g₀
    G₁ = (g₀ + g₁ + g₂) / 2
    G₂ = (g₀ - g₁ + g₂) / 2
    G₃ = g₂
    （对应变换矩阵 G = [[1,0,0],[1/2,1/2,1/2],[1/2,-1/2,1/2],[0,0,1]]）

步骤 2  把当前输入 tile 变换到 Winograd 域（每次 forward 都做）：
    D₀ = d₀ - d₂
    D₁ = d₁ + d₂
    D₂ = d₂ - d₁
    D₃ = d₁ - d₃

步骤 3  Winograd 域做点乘（只有这 4 次是乘法）：
    M₀ = D₀·G₀,  M₁ = D₁·G₁,  M₂ = D₂·G₂,  M₃ = D₃·G₃

步骤 4  反变换还原输出（全是加减法）：
    y₀ = M₀ + M₁ + M₂
    y₁ = M₁ - M₂ - M₃
```

**数一下操作量：**

```
标准卷积（2个输出）：
    乘法 6次，加法 4次

Winograd：
    步骤1 ≈ 4次加减（预计算，忽略）
    步骤2   4次加减（0次乘法！）
    步骤3   4次乘法
    步骤4   4次加减
    ─────────────────────
    乘法 4次，加法 12次
```

加法看起来多了，为什么还快？两个原因：

**原因1：乘法比加法贵（历史说法，现代 GPU 上不成立）**

| 时代 | 硬件 | 乘法 vs 加法 |
|------|------|-------------|
| 1980s-90s | x87 FPU (8087) | FMUL 比 FADD 慢 ~1.5-2× |
| 早期 GPU | Tesla/Fermi | multiply 略贵 |
| **现代 GPU** | **Ampere/Ada/Hopper** | **FP32 mul = FP32 add，吞吐完全相同** |
| Tensor Core | FP16/BF16 | FMA（`a*b+c`）是一条融合指令，mul+add 合一 |

**NVIDIA GPU 架构代号速查**（每代用科学家名字命名，Volta 是第一个引入 Tensor Core 的架构）：

| 代号 | 发布年 | 消费级 | 数据中心 | 备注 |
|------|--------|--------|---------|------|
| Volta | 2017 | 无 | V100 | 首次引入 Tensor Core |
| Ampere | 2020 | RTX 3090/3080 | A100 | 大部分实验室主力 |
| Ada Lovelace | 2022 | RTX 4090/4080 | L40 | 新工作站 |
| Hopper | 2022 | 无 | H100/H200 | 顶级集群 |
| Blackwell | 2024 | RTX 5090 | B200 | 最新一代 |

架构代号 = 一整套芯片设计方案（流水线结构、缓存大小、新增硬件单元等），**不是软件，是刻在硅晶体管上的物理电路**。

---

**时钟周期与吞吐量**

GPU 有一个时钟频率，如 A100 = 1.41 GHz，每秒跳动 14.1 亿次，每"跳"一次 ≈ 0.7 纳秒，这就是一个时钟周期。

"吞吐"和"延迟"是两回事，用流水线工厂理解：

```
一道菜需要4步（洗→切→炒→装），每步1分钟，延迟 = 4 分钟

一个厨师（串行）：每4分钟出1道菜，吞吐 = 0.25 道/分钟

4个厨师流水线并行：
  第1分钟：洗A
  第2分钟：切A，洗B
  第3分钟：炒A，切B，洗C
  第4分钟：装A出菜，炒B，切C，洗D
  第5分钟：装B出菜，炒C，切D，洗E
  延迟还是4分钟，但吞吐 = 1道/分钟，提升4倍
```

GPU 的 FP32 加法延迟 ~4 个周期，但 CUDA Core 内部就是4级流水线，**每周期都能接收一个新操作**，所以单核吞吐 = 1 op/周期。

"一个时钟周期一次计算"的准确含义：

```
每个 CUDA Core：每周期"启动"一次 FMA（不是完成，是进入流水线）
              → 4周期后出结果，但期间每周期都有新操作进入

A100 整卡：6912 个 CUDA Core 同时各自启动
         → 每周期完成 6912 次 FMA = 6912×2 = 13824 FLOPs
         → 13824 × 1.41GHz ≈ 19.5 TFLOPS（FP32理论峰值）
```

---

**CUDA Core vs Tensor Core：两种不同的物理电路，同时存在于一块芯片**

```
A100 芯片内部（108 个 SM）：
每个 SM 内：
  ├── 64 个 FP32 CUDA Core  ← 通用，什么都能算
  ├──  4 个 Tensor Core     ← 专用，只做矩阵乘加，但快很多
  └── 32 个 FP64 CUDA Core
```

程序员写普通 CUDA 用 CUDA Core，调用 cuBLAS/cuDNN 矩阵乘法时框架自动调度 Tensor Core。

---

**Tensor Core 怎么做到的（专用硬件乘法树+加法树）**

Tensor Core 每周期完成 `D = A×B + C`，其中 A、B、C、D 是 4×4 矩阵。展开来看：

```
D[0][0] = A[0][0]·B[0][0] + A[0][1]·B[1][0] + A[0][2]·B[2][0] + A[0][3]·B[3][0] + C[0][0]
```

16 个输出，每个需要4次乘+累加，共 **64 次 multiply-accumulate**。

```
CUDA Core 做法（通用，灵活）：   串行执行64条指令，64个周期
Tensor Core 做法（专用，定制）：
    64个并行乘法器同时运算
         ↓ ↓ ↓ ↓ ... (64路)
    硬件加法树汇总（像锦标赛括号）
         ↓
    1个周期出16个结果
```

代价：Tensor Core 只能做矩阵乘加，不能做其他运算。矩阵维度必须是16的倍数（FP16/BF16），否则无法填满，退回 CUDA Core。这就是 depthwise 卷积慢的根本原因——矩阵退化为 [1, k³, spatial]，Tensor Core 完全用不上。

---

**FMA（Fused Multiply-Add，融合乘加）为什么更快**

FMA 做的运算量和分开算完全一样，快不是因为"少算了"，而是工程上省了：

```
分开算（2条指令）：
  ① tmp = a * b    → 乘法完成，结果写回寄存器文件（有总线延迟）
  ② c   = tmp + c  → 从寄存器读 tmp，做加法

FMA（1条指令）：
  c = a * b + c    → 乘法器出口直接接加法器入口，中间结果不经过寄存器
```

| 省在哪 | 说明 |
|--------|------|
| 省一次寄存器读写 | tmp 不需要写入/读出寄存器文件 |
| 少一条指令派发 | 指令调度器处理1条而非2条 |
| 精度更高 | 中间结果不截断，最后才舍入，误差更小 |
| 流水线连续 | 乘法器输出直接流入加法器，物理上就是连着的导线 |

现代 GPU 的 CUDA Core 本质上是乘法器+加法器串联的流水线，`a*b` 的结果直接流进加法器，不经过寄存器总线。所以"1 FMA = 2 FLOPs，但只用1个周期"是真实的——两步被流水线化到同一周期里。

这也是为什么 FLOPs 计数将乘法和加法等价：**1 MAC = 1 mul + 1 add = 2 FLOPs**，两者成本相同。

因此 Winograd 把 6 次 mul 换成 4 次 mul + 12 次 add，总操作量实际上变多了。
在现代 GPU 上，cuDNN 用 Winograd 的真正理由不是"乘法便宜了"，而是下面的原因2。

**原因2（现代 GPU 上的真实原因）：步骤2的输入变换被所有输出通道共享**

实际卷积有 C_out 个输出通道，每个通道用不同的 kernel：

```
标准卷积：
    对每个输出通道 c = 1..C_out，各算一遍：6次乘法 + 4次加法
    总共 C_out × (6乘 + 4加)

Winograd：
    步骤2（输入变换）：只做一次！4次加减。C_out 个通道共用同一份变换结果
    步骤3：每个输出通道各做 4次乘法
    步骤4：每个输出通道各做 4次加减
    总共 4加（步骤2，共享）+ C_out × (4乘 + 4加)
          ↑
          这个"4加"是步骤2的4次加减法，整个 C_out 只做1次，是常数项（与C_out无关）
          C_out=320时：4加 ≈ 可忽略，主要节省是 320×6=1920乘法 → 320×4=1280乘法
```

C_out=320 时，步骤2 只做 1 次，省下来的乘法 × 320 很可观。

3D k=3：三个维度分别做变换 → 乘法从 27 次降到约 8 次，**省 ~70%**。

**为什么 stride=1 才能用？**

stride=1 时相邻窗口重叠 k-1=2 个元素，重叠越多提取公共项越合算。
stride=2 时窗口跳格，[d₀,d₁,d₂] 和 [d₂,d₃,d₄] 只共享 d₂ 一个，
公共项太少，变换矩阵的结构就不成立了。

**为什么 depthwise（groups=C）不行？**

Winograd 快的核心在于**步骤2（输入变换）被 C_out 个通道共享**。
depthwise 每组只有 C_out=1，步骤2 根本没有通道可以共享：

```
标准 Conv（C_out=320）：
    步骤2 输入变换：做 1 次（4次加减）
    步骤3 乘法：320 个通道各做 4 次 = 1280 次乘法
    对比标准：320 × 6 = 1920 次乘法
    → 省了 640 次乘法（共享摊销的收益）

depthwise（groups=320，每组 C_out=1）：
    步骤2 输入变换：每组各做 1 次 = 做 320 次（无法共享！）
    步骤3 乘法：每组 4 次 = 320 × 4 = 1280 次乘法
    变换开销 + 乘法 >> 直接算的 320 × 27 次乘法
    → 共享优势为零，变换反而是额外负担
```

Winograd 域的矩阵乘也从 [C_in, C_out] 退化为 C 个 [1,1] 标量乘，
Tensor Core 完全用不上。cuDNN 干脆不实现 depthwise Winograd，直接 fallback。

###### 为什么 depthwise 用不上 Tensor Core：im2col 视角

卷积在 GPU 上实际是通过 **im2col** 变成矩阵乘来执行的。

**im2col 原理**：卷积核每滑动到一个输出位置，就从输入里取一块 k×k×k 的 patch。
把这个 patch 展平成一列，所有输出位置的列并排拼成矩阵 X：

```
1D 例子（输入5个数，核k=3，步长1，3个输出位置）：

核滑动：
  输出位置0 → 覆盖 [d₀,d₁,d₂] → 展平 → 第0列
  输出位置1 → 覆盖 [d₁,d₂,d₃] → 展平 → 第1列
  输出位置2 → 覆盖 [d₂,d₃,d₄] → 展平 → 第2列

im2col 矩阵 X，形状 [k=3, 输出位置数=3]：
         位置0  位置1  位置2
  行0  [ d₀    d₁    d₂  ]
  行1  [ d₁    d₂    d₃  ]
  行2  [ d₂    d₃    d₄  ]

W = [k₀, k₁, k₂]，形状 [1, 3]

W @ X = [k₀d₀+k₁d₁+k₂d₂,  k₀d₁+k₁d₂+k₂d₃,  k₀d₂+k₁d₃+k₂d₄]
         输出位置0           输出位置1           输出位置2
```

d₁、d₂ 在多列里重复出现，这是相邻 patch 重叠造成的（im2col 会复制数据）。

上面例子是单通道（C_in=1）。若有多个输入通道，每列要把**所有通道的 patch 全部拼接进来**：
```
C_in=2，k=3 时，输出位置0 对应的列：
  [通道0的d₀,d₁,d₂,  通道1的e₀,e₁,e₂]  ← 长度 = C_in×k = 2×3 = 6
```
这就是为什么 X 的行数是 C_in×k³ 而不是 k³。
标准卷积一次矩阵乘把所有通道的信息都融合进去；depthwise 的 X_c 每列只有通道 c 自己的 k³ 个值，通道间完全不混。

**3D 卷积的 im2col**：核覆盖 k×k×k=343 个体素，每个 patch 展平成343维列向量。
`spatial = D_out × H_out × W_out` = **输出体积里的位置总数**（三维坐标线性编号成列索引）。
例如输出体积 56×56×28，则 spatial = 87808，X 矩阵有 87808 列。

X 的每一列 = **为了算出该输出位置的值，需要从输入里读取的那块数据**（k×k×k 个输入体素展平），是输入数据，不是输出数据。输出是 W @ X 之后才有的。

**标准卷积 vs depthwise 的矩阵形状对比**（C_in=64, C_out=128, k=3）：

```
标准卷积：
  W：[C_out=128,   C_in×k³ = 64×343 = 21952]
        ↑ 128行，每行=一个输出通道的权重（覆盖所有输入通道）
  X：[C_in×k³=21952,   spatial=D_out×H_out×W_out]
        ↑ 每列=计算该输出位置所需的输入 patch（所有C_in通道拼接展平）
  输出 = W @ X → [128, spatial] → reshape → [128, D_out, H_out, W_out]
  M=128，K=21952，N=spatial → Tensor Core 可用 ✓

Depthwise（每个通道 c 独立计算）：
  W_c：[1,    k³=343]
         ↑ 1行，只有1个输出通道
  X_c：[k³=343,   spatial]
         ↑ 每列=计算该输出位置所需的输入 patch（仅通道c的343个体素展平）
  输出 = W_c @ X_c → [1, spatial] → 这就是通道c的输出
  M=1，K=343，N=spatial → Tensor Core 要求 M≥16，直接不满足 ✗

  重复 C=320 次（每个通道各自算一遍）
```

能不能把 320 个通道合并进一个矩阵？不行：
- 不同通道 c 用不同的输入 patch（X_c 各不相同）
- 不同通道 c 用不同的权重（W_c 各不相同）
- 无法拼成一个标准的密集矩阵乘，只能做320个独立的 [1,343]×[343,spatial] 矩阵乘
- 每次 M=1，Tensor Core 永远填不满

###### FFT 卷积数学原理

**FFT 公式（DFT 的快速算法）**：把长度 N 的时域序列 x[n] 变换到频域 X[k]
```
        N-1
X[k] =  Σ  x[n] · e^(-j2πkn/N)      k = 0, 1, ..., N-1
        n=0
```
- k = 频率编号（第 k 个频率分量）
- e^(-j2πkn/N) = cos(2πkn/N) - j·sin(2πkn/N)，是一个旋转因子
- 结果 X[k] 是复数，模 = 该频率的幅度，辐角 = 相位

**IFFT 公式**（逆变换，频域 → 时域）：
```
        1   N-1
x[n] = ─── Σ  X[k] · e^(j2πkn/N)    n = 0, 1, ..., N-1
        N  k=0
```
和 FFT 公式的区别：指数符号取反（e^+j 而非 e^-j），最后除以 N。

---

**深度学习里的"卷积"实际上是互相关（cross-correlation），没有翻转**

数学上严格的卷积定义要翻转 kernel：
```
严格卷积：  (x * w)[n] = Σ x[m] · w[n - m]     ← w[n-m] 是 w 关于 n 的翻转再平移
互相关：    (x ⋆ w)[n] = Σ x[n + m] · w[m]     ← w 不翻转，直接滑动
```

PyTorch / cuDNN 的 Conv3d 实现的是**互相关**（不翻转 kernel），但约定俗成叫"卷积"。
翻不翻没有实质区别：kernel 是学出来的，如果任务需要"翻转后的权重"，梯度下降会直接学到翻转的值。

卷积定理严格成立于有翻转的那个定义。对于互相关，等价关系变成：
```
(x ⋆ w)[n] = IFFT( FFT(x) · conj(FFT(w)) )
```
conj = 共轭（复数的虚部取反）。由于 w 是实数，conj(FFT(w)) = FFT(flip(w))。
cuDNN 内部对 kernel 做一次预翻转再走 FFT 路径，结果就是正确的互相关，对外接口透明。

**卷积定理**：时域卷积 = 频域点乘
```
(x * w)[n] = IFFT( FFT(x) · FFT(w) )
```

步骤：
```
① 补零：把 x 补到长度 N+k-1（避免循环卷积混叠）
② FFT(x)  —— O(N log N)
③ FFT(w)  —— O(k log k)，权重固定可缓存
④ 频域点乘  —— O(N)，只是逐元素乘
⑤ IFFT    —— O(N log N)
```
当 k 很大时：标准卷积 O(N·k³)，FFT O(N log N)，FFT **大幅节省**。

**限制**：stride > 1 时 FFT 计算的是所有位置的输出，再下采样 = 浪费。
cuDNN 没有为 stride≥2 的 FFT 实现高效路径。

###### implicit GEMM（im2col）数学原理

把卷积**等价转换为矩阵乘法**：
```
步骤 1  im2col：
    对每个输出位置，取输入的 k×k×k patch，展平成列向量
    → 矩阵 X，形状 [k³·C_in,  D_out·H_out·W_out]

步骤 2  权重矩阵：
    W，形状 [C_out,  k³·C_in]

步骤 3  矩阵乘：
    Y = W @ X，形状 [C_out,  D_out·H_out·W_out]
    这步调用 cuBLAS，可用 Tensor Core（需矩阵维度是 16 的倍数）

步骤 4  reshape 回 [C_out, D, H, W]
```

**depthwise 的问题**：groups=C 时，每个 group 的矩阵大小只有 [1, k³, spatial]，
矩阵太小，Tensor Core 发挥不了，退化为小矩阵 fallback。

三种版本的 Encoder 对比（Dataset003_Liver 实际配置：6 stage，每 stage 2 conv）：

```
             原始 nnUNet             DWBot3D（朴素）          IBBot3D（本方案）

DWBot3D：5 个 stride=2 conv 全换成 DWSep(k=7,s=2) → 5 处 ❌ 极慢
IBBot3D：5 个 stride=2 conv 全部保留 k=3      → 0 处问题，大核只在 stride=1
```

**实测数据**（DW7, k=7, stride=2, C=320）：
- 标准 Conv3d(k=3, s=2)：~48 s/epoch
- DWSep(k=7, s=2) 替换后：~514 s/epoch（**10× 变慢**）

**问题 2：架构上也不对**

朴素替换中 DWSep 的结构是：
```
DW → PW → Norm → Activation
```
大核只做了特征提取，没有 residual connection，非线性能力没有增强。
这不是 MedNeXt 的思路，只是把卷积核换大了。

---

##### 方案 B：倒置瓶颈块（`MLAUNetIBBot3D`，当前正在训练）

**实测速度**：~288 s/epoch（baseline ~48 s，仍慢 6×，需 profiling 定位瓶颈）

MedNeXt 的核心设计：**大核 ONLY 在 stride=1 的 depthwise**，下采样单独处理。

###### IBConvBlock3D 内部结构

```
输入 x (B, C, D, H, W)
│
├─────────────────────────────────┐
│                                 │  残差分支
│                                 │  C_in == C_out → Identity
│                                 │  C_in != C_out → Conv3d(1×1×1)
▼                                 │
DW(k×k×k, groups=C, stride=1)    │  ← 大核空间混合
↓          (C → C，通道不变)      │    stride 永远为 1
InstanceNorm3d(C)                 │
↓                                 │
PW_expand(1×1×1)                  │  ← 1×1×1 点卷积，Tensor Core 友好
↓   C → 4C（倒置瓶颈扩张）        │
GELU                              │
↓                                 │
PW_compress(1×1×1)                │
↓   4C → C                       │
└──────────── + ──────────────────┘
              ↓
           输出 (B, C, D, H, W)
```

###### Encoder 中的替换对比（Stage 1 为例）

```
                DWBot3D（朴素）              IBBot3D（本方案）
               ┌──────────────────┐        ┌──────────────────────────────┐
Stage 1        │ DWSep(k=7, s=2)  │ ❌慢   │ ConvDropoutNormReLU(k=3, s=2)│ ✓ 原样保留
               │ DWSep(k=7, s=1)  │ ✓     │ IBConvBlock3D(k=7, s=1)      │ ✓ 大核在这里
               └──────────────────┘        └──────────────────────────────┘
                         ↑                              ↑
               把下采样也大核化了                  下采样不动，只替换 stride=1
```

stride=2 的下采样 **保持原始 ConvDropoutNormReLU 不动**（标准 3×3×3 卷积）。

---

##### 参数量对比（以 C=128, k=7 为例）

| 方案 | 计算公式 | 参数量（C=128）|
|------|----------|----------------|
| 标准 Conv3d (k=3) | k³·C_in·C_out = 27·128·128 | 442,368 |
| 标准 Conv3d (k=7) | k³·C_in·C_out = 343·128·128 | 5,619,712 |
| DWSep (k=7) 朴素 | k³·C_in + C_in·C_out = 343·128 + 128·128 | 60,288 |
| **IBConv (k=7)** | k³·C_in + 2·exp_r·C·C = 343·128 + 2·4·128·128 | **175,872** |

IBConv 比标准 k=3 参数少 60%，比朴素 DWSep 稍多（多了 expand/compress），但架构更合理。

---

##### 感受野对比

| 卷积核 | 单层感受野（体素数） | 6 层叠加后感受野 |
|--------|---------------------|-----------------|
| k=3 | 3³ = 27 | (3-1)×6+1 = 13 |
| k=5 | 5³ = 125 | (5-1)×6+1 = 25 |
| **k=7** | 7³ = 343 | **(7-1)×6+1 = 37** |

肝脏肿瘤分割中，大感受野对捕获大病灶边界有直接帮助。

---

##### 速度影响（预期）

| 操作 | cuDNN 路径 | 速度预期 |
|------|-----------|----------|
| DWSep(k=7, s=2) 朴素 | grouped large-kernel strided → fallback | **极慢**（实测 10×）|
| DWSep(k=5, s=2) | 同上，略好 | 仍慢 2-3× |
| IBConv(k=7, s=1) depthwise | grouped, stride=1, 可用 implicit GEMM | 正常 |
| stride=2 保持 Conv3d(k=3, s=2) | Winograd/FFT 不适用 s=2，但 3×3 还是最优路径 | 正常 |

IBBot3D 的训练速度应接近 baseline（无大核步长问题）。
