# 方法论文的研究问题定义与创新来源

> 记录日期：2026-08-29  
> 记录性质：论文阅读与研究方法论笔记  
> 证据范围：UNETR、ConvNeXt、MedNeXt、Swin UNETR、nnU-Net 和 MedSAM 的表述基于原文摘要/引言核对；U-Net、Transformer、ViT、Swin Transformer 和 SAM 为后续补充的问题定义归纳；本笔记不等同于系统文献综述

## 1. 核心结论

> **“定义问题”不等于“必须分析具体失败病例”。**

很多顶尖方法论文确实没有从 case-level failure analysis 出发。它们定义的问题常常位于更抽象的方法、设计空间、技术范式或系统层。数据集在这类工作中主要用于验证研究命题，不一定是发现问题的起点。

因此，以下两个判断需要同时成立：

1. 说“这些论文完全没有定义问题”过于绝对。
2. 说“它们都通过分析具体失败病例来定义问题”也不符合原文。

真正的分歧在于：日常讨论中的 `problem` 可能指广义的 research problem，而自己之前理解的 `problem` 更接近“从具体数据或病例中归纳出的稳定失败模式”。

## 2. 四种创新起点

### 2.1 Failure-driven

起点是可重复观察的具体失败现象：

```text
具体失败现象
→ 分析稳定失败模式
→ 定义可验证的任务问题
→ 设计针对性方法
```

例如：小肿瘤漏检、无肿瘤病例假阳性、跨域性能骤降。这是导师要求开展失败病例分析时指定的创新来源，但不是唯一合法的研究路线。

### 2.2 Limitation-driven

起点是现有方法的结构性限制：

```text
现有方法的结构限制
→ 受限的表征或能力
→ 选择能补足该能力的机制
→ 新架构
```

UNETR 是典型例子：将卷积的局部性与长距离空间依赖建模受限联系起来，再引入 Transformer encoder。这是明确的 method-level problem，并不需要以某类失败 CT slice 作为起点。

### 2.3 Opportunity / paradigm-driven

起点是新技术、新设计原则或新范式带来的可研究空间：

```text
新技术或新设计空间
→ 提出研究命题
→ 系统地现代化或重组旧范式
→ 通过 benchmark 验证
```

ConvNeXt 的问题不是“CNN 在哪些图片上失败”，而是“纯 ConvNet 在吸收 Transformer 时代的现代设计后，能否继续与 Transformer 竞争”。Swin UNETR 的 self-supervised pretraining 工作也带有明显的机会驱动特征：将 SSL 与 Swin Transformer 在 3D 医学影像中组合并验证。

### 2.4 System-level problem-driven

起点是领域整体工作流或能力边界中的问题：

```text
领域工作流缺陷
→ 定义系统级目标
→ 构建可复用的方法或平台
→ 在多数据集/多任务上验证
```

nnU-Net 针对不同数据集需要专家手工配置流水线的问题，通过 dataset fingerprint 自动配置预处理、网络、训练和后处理。MedSAM 针对医学分割模型过于 modality-specific 或 disease-specific、缺少跨任务泛化能力的问题，提出通用医学分割基础模型。

## 3. 十一篇代表论文的问题定义

下表不是对每篇论文所有贡献的概括，而是为了识别其最主要的研究命题及所在层级。

| 论文 | 它真正定义的问题 | 问题层级 |
|---|---|---|
| **U-Net** | 标注医学图像很少，如何在少量训练样本下仍实现精确定位和分割？ | 任务 + 方法 |
| **Transformer** | 序列建模是否必须依赖 recurrence 或 convolution？能否只使用 attention？ | 范式级方法问题 |
| **ViT** | 图像识别是否真的必须依赖 CNN？纯 Transformer 能否直接处理 image patches？ | 范式级方法问题 |
| **Swin Transformer** | Vanilla ViT 不适合作为通用视觉 backbone：高分辨率计算贵，且视觉目标尺度变化大，如何解决？ | 架构级方法问题 |
| **ConvNeXt** | Transformer 的优势究竟来自 Transformer 本身，还是现代 architecture design？纯 CNN 现代化后能达到什么程度？ | 设计空间问题 |
| **UNETR** | 3D segmentation 中卷积的局部性限制 global / long-range dependency 建模，Transformer 能否作为 encoder？ | 方法 limitation |
| **Swin UNETR** | 大规模 3D 医学标注昂贵，能否用 self-supervised pretraining + hierarchical Transformer 学习可迁移的 3D anatomy representation？ | 数据稀缺 + 方法 |
| **nnU-Net** | 为什么医学分割方法换一个数据集就需要大量专家手工配置？能否让 pipeline 根据数据集自动配置？ | 系统级问题 |
| **SAM** | 能否把 segmentation 从大量固定任务统一成一个 promptable task，并实现 zero-shot transfer？同时如何获得足够大规模的 segmentation data？ | 范式 + 数据系统 |
| **MedSAM** | 医学分割模型通常针对特定 modality 或 disease，能否构建跨模态、跨疾病的通用医学分割 foundation model？ | 系统/泛化问题 |
| **MedNeXt** | Transformer 很强，但在医学数据有限的条件下，现代纯 ConvNet 能否通过 large kernel + scaling 达到强性能？ | 方法设计空间 |

## 4. 对其中六篇论文的进一步理解

### UNETR

原文明确将 FCNN 的卷积局部性视为长距离空间依赖学习的限制，因此它不能被描述为“没有定义问题”。它的问题是方法层限制，而不是小肿瘤等任务层失败。

### ConvNeXt

它研究的是 architecture design space：Transformer 的优势究竟来自 attention 本身，还是一整套现代架构设计？作者从 ResNet 出发，逐步引入 Transformer 时代的设计并观察贡献。因此，ImageNet 在这里主要是 benchmark，而不是失败现象的发现地。

### MedNeXt

它的问题是如何将现代 ConvNet 与 scaling 思想适配到数据稀缺的 3D 医学分割。large kernel、ConvNeXt-like block、residual up/downsampling、kernel scaling 和 compound scaling 是对该方法空间问题的回答。这不是对某类 CT 肿瘤失败的专项研究。

### Swin UNETR

这项工作同时使用大规模专家标注 3D 数据集难获得的 limitation，以及 SSL + Swin Transformer 的新技术机会。其核心更接近“构建一个 3D 医学影像自监督预训练框架并验证”，而不是查找特定分割失败模式。

### nnU-Net

它是明确的 problem-motivated methodology：生物医学分割流水线高度依赖数据集属性与硬件条件，专用方案的手工设计困难、成本高且不易复现。它解决的是流水线配置问题，不是单一 lesion failure。

### MedSAM

它针对的是现有医学分割方法通常只服务于特定模态或疾病、缺少跨任务泛化能力的系统级问题。其大规模多模态数据用来支撑 universal medical image segmentation 这一研究目标。

## 5. 对当前课题的含义

不应把顶尖 method paper 的论文生成路径误读为“每篇都先完成病例级 failure analysis”，也不应因为某篇论文没有这样做就判断它“没有问题”。

导师要求分析失败病例，是在为当前课题指定一条更具体、更容易建立数据证据链的 **failure-driven problem discovery** 路线。这是适合当前肝肿瘤分割课题的创新来源，不是对所有方法研究的统一要求。

与导师或学姐讨论时，可以使用下面这个更精确的表述：

> 我以前说顶尖方法论文“不定义问题”不准确。现在我的意思是：很多顶尖 method papers 不做 case-level failure-driven problem discovery，它们的问题通常来自方法限制、设计空间或新的技术范式；而老师让我做的，是另一种从数据和 failure 中发现具体问题的研究路线。

## 6. 后续使用时的判断问题

阅读一篇新论文时，不再只问“它有没有问题”，而是分别问：

1. 它的 research problem 是任务层、方法层、范式层还是系统层？
2. 问题的证据来自病例失败、已知结构限制、新技术机会，还是领域工作流缺陷？
3. 数据集是用来发现问题，还是主要作为 benchmark 验证命题？
4. 论文的方法是否真正对应前面定义的问题？
5. 实验能否区分“方法有效”与“对问题的解释正确”？

## 8. 当前个人目标：建立“问题—结构—证据”闭环

> 追加日期：2026-08-30  
> 当前目标：不是继续堆叠现成模块，而是找到一个真实、具体、可验证的问题，围绕它设计由自己规定内部数据流的核心机制，再用针对性实验证明该机制解决的正是所声称的问题。

目前已经具备的基础包括：

- 有成熟的 baseline / backbone；
- 能够修改网络并运行实验；
- 能够进行不同模型和 trainer 的比较；
- 已经开始分析 failure、小肿瘤和跨数据集问题。

当前真正需要补齐的是下面的完整闭环：

$$
\boxed{
\text{明确问题}
\rightarrow
\text{针对问题设计核心结构}
\rightarrow
\text{用实验形成直接证据}
}
$$

### 8.1 第一优先级：先找到并固定一个可验证的问题

当前最近的目标不是立即发明模块，而是先找到一个能够写进 Introduction、也能够被实验推翻的问题。问题不能只写成：

> 我想提高 Dice。

它至少需要包含：

1. **具体对象**：哪类病例、病灶尺度、数据域或系统环节存在问题；
2. **稳定现象**：问题能否在多个病例、trainer、随机种子或数据域中重复观察；
3. **候选原因**：现有结构或监督机制为什么可能导致该现象；
4. **可证伪预测**：如果解释正确，针对性干预后哪些指标或病例亚组应该改善；
5. **边界条件**：什么结果出现时，应承认原解释不成立。

例如，下面只能作为候选问题模板，不能在没有证据时直接写成结论：

> 现有模型在小肿瘤上的表现显著弱于大肿瘤；如果主要原因是多次下采样造成细粒度病灶特征丢失，那么保留高分辨率局部信息的针对性机制应主要改善 small-lesion 指标，而不是只带来无差别的总体 Dice 波动。

或：

> Encoder 与 decoder 特征对不同尺度病灶的有效贡献可能不同；如果固定 skip fusion 是限制因素，那么自适应融合机制的收益应随病灶尺度或错误类型呈现可解释差异。

Small lesion、skip fusion、跨数据集监督冲突目前都是候选入口，尚未固定为最终论文问题。最终选择应由失败证据、现有方法限制、文献空缺和可执行实验共同决定。

#### 8.1.1 可以宽松找，但不能随便编

问题不必是全领域最重大、最新或最复杂的问题。为了尽快形成可发表闭环，可以优先选择最容易稳定复现、最容易设计针对性机制、也最容易进行分组验证的问题。可接受的候选包括：

- 小肿瘤表现明显弱于大肿瘤；
- 模糊边界区域误差较大；
- 高层语义与低层细节采用固定融合，无法根据病例或尺度调整贡献；
- 多尺度目标下单一感受野表现不稳定；
- 跨数据集性能明显下降；
- 某类病例或病灶容易漏检。

这些问题可以普通，但不能是先决定模块以后才编造出来的理由。一个“够用的问题”至少满足三个硬条件：

1. **Baseline 中真实存在**：能够由指标、病例或可视化稳定观察，而不是依靠主观挑图；
2. **机制直接对应**：模块中的关键设计能够逐项对应候选原因，例如 small lesion 对应高分辨率 detail branch，多尺度问题对应 scale-aware fusion；
3. **能够单独验证**：除 Overall Dice 外，还能通过分组指标、消融或配对病例判断目标问题是否真的改善。

因此，问题筛选时采用的功利标准是：

> **问题不一定很重大，但必须真实、可复现，并且能够被核心机制直接改善。**

“问题不新”本身不等于不能发表。很多方法论文研究的是已有问题，其主要新意来自：针对这个问题提出了新的、具体的机制。但如果 Baseline 中看不到该问题，或实验无法区分目标机制与普通涨点，就不能为了配合已经想好的模块硬写问题动机。

#### 8.1.2 最短的现实执行路线

```text
先获得可信的 Baseline 结果
→ 从真实结果中寻找最容易稳定复现的问题
→ 固定问题、候选原因和可证伪预测
→ 围绕它设计一个自己的核心机制
→ 做公平对照、机制消融和对应的分组指标
→ 对应关系成立后再进入论文写作
```

这里的“开始写论文”不是只要 Overall Dice 上涨就成立，而是至少已经看到：Baseline 中问题存在、目标亚组按预期改善、关键机制消融支持解释，并且没有用总体平均掩盖明显退化。

### 8.2 第二步：设计真正属于自己的核心机制

“自己的模块”不要求发明全新的卷积、注意力或数学运算。原创性可以来自作者自己规定：

- 模块接收什么输入以及输入来自网络哪一层；
- 数据分成几条路径，每条路径负责什么信息；
- 特征之间如何交互，权重如何生成；
- 不同尺度、局部和上下文信息如何融合；
- residual 如何连接；
- 输出送到哪里，以及为什么能影响目标问题。

因此，一个核心原创模块就可能足够。评价重点不是框图中有多少组件，而是内部 tensor flow 是否由问题推导出来、每一步是否有清楚作用，并且是否能通过消融验证。不能把多个现成模块拼接后统一称为原创机制。

### 8.3 第三步：证明机制解决的就是所声称的问题

如果声称解决 small-lesion failure，证据不能只有总体 Dice 上升，还应至少比较：

| 方法 | Small lesion | Medium lesion | Large lesion | Overall |
|---|---:|---:|---:|---:|
| Baseline | 待测 | 待测 | 待测 | 待测 |
| Baseline + proposed mechanism | 待测 | 待测 | 待测 | 待测 |

理想证据模式是：目标亚组显著改善，非目标亚组没有明显受损，并且改善能够在配对病例、可视化和消融中被追踪。若各尺度只出现近似一致的小幅波动，则证据更支持“整体正则化或容量变化”，不能直接归因于解决了小肿瘤问题。

针对任何候选问题，最终证据至少应覆盖：

- Baseline 与核心机制的公平对照；
- 核心路径、权重或融合方式的消融；
- 与问题直接对应的分层指标；
- 配对病例及失败案例变化；
- Liver、Tumor、Overall 与各数据域结果，避免总体均值掩盖退化；
- 参数量、计算量、显存或训练成本；
- 完整预测、`summary.json`、文本报告、可视化和 checkpoint provenance。

### 8.4 当前阶段的完成标准

只有同时完成以下三项，才形成一项可交付的方法论文工作：

1. **问题成立**：有重复、分层且可审计的证据证明问题真实存在；
2. **结构对应**：核心机制中的每条主要数据流都能对应问题假设，而不是事后解释；
3. **证据闭环**：针对性实验表明目标问题得到改善，并如实报告无效、退化、成本和适用边界。

当前阶段的第一完成点是：

> **先从 failure-driven、method/system-driven 或 paradigm/field-driven 入口中，找到并固定一个满足上述条件的具体问题。**

### 8.5 一句话目标

> **我的目标不是再拼三个模块，也不是只让总体 Dice 偶然上涨，而是完成一个“真实问题—自有核心结构—针对性证据”的闭环；当前最优先的任务，是先找到那个值得解决且能够验证的问题。**

更现实的执行原则是：

> **问题可以普通，但不能假；模块可以借鉴已有思想，但内部数据流和组合方式要有自己的设计；实验必须证明它确实解决了这个问题。**
