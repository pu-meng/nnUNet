> **本机 Mihomo v1.19.13**，HTTP 代理端口 `7892`，管理 API 端口 `9091`。
> 规则模式（Rule）运行，订阅来源：扬帆云（yfssce.net）。
>
> ⚠️ 端口 7891 被用户 ZhaoPu 的 clash 占用，本用户固定用 **7892**。

## 零、背景知识（先看这里）

### Clash 和 Mihomo 是什么关系

```
Clash（旧版，2023年作者删库停止维护）
  ↓ 社区接手代码继续开发，改名
Mihomo（新版，即 Clash Meta）
```

功能完全一样，配置文件格式兼容，只是二进制文件名变了，新版支持更多协议（vless、anytls 等）。
配置目录还叫 `.config/clash/` 完全没问题，目录名只是个文件夹名字，不影响任何功能。

为什么从 clash 换到 mihomo：
- `/usr/bin/clash`（系统旧版）→ 报错 `unsupport proxy type: vless`
- mihomo v1.18.10 → 报错 `unsupport proxy type: anytls`
- **mihomo v1.19.13** → 全部协议支持，跑起来了 ✓

### 文件结构
```
~/bin/mihomo                        ← 可执行文件（程序本身）
~/.config/clash/
  yangfan.yaml                      ← 扬帆云订阅配置（节点列表+规则）
  geoip.metadb                      ← 地理IP数据库（手动提供，服务器访问GitHub被封）
  cache.db                          ← Mihomo 缓存
```

### 流量完整路径
```
Claude Code（本地程序）
  ↓ 读取环境变量 HTTPS_PROXY=http://127.0.0.1:7892
Mihomo（监听 7892 端口，等待请求）
  ↓ 内部第一步：规则引擎
    DomainKeyword/anthropic → 走代理
    GEOIP/CN               → 直连
  ↓ 内部第二步：策略组"扬帆云"选节点
    当前选：level1-法国01
  ↓
校园网出口 219.231.133.120
  ↓ 穿过 GFW（美国节点被封，法国节点可通）
法国中转节点（level1-法国01）
  ↓
api.anthropic.com ✓
```

### 常见概念答疑

**IP 地址（219.231.133.120）是什么**
网络世界的"门牌号"，告诉互联网上其他机器数据包要寄到哪里。

**端口是什么，7892 是谁建的**
端口不是服务器提前建好的房间，是**程序动态申请的**。Mihomo 启动时向操作系统申请 7892 这个端口，停止时释放。ZhaoPu 的 clash 先申请了 7891，你的 Mihomo 来晚了改申请 7892。

**监听是什么意思**
Mihomo 坐在 7892 号窗口等待。谁来找 7892，Mihomo 就接待谁。

**HTTPS_PROXY 管的是谁**
只影响当前用户（PuMengYu）在设置了这个变量的终端里运行的程序。ZhaoPu 不受影响，root 不受影响。

**curl/wget 是命令还是程序**
两者不矛盾。命令是你叫它的名字，程序是磁盘上的可执行文件。`which curl` 返回 `/usr/bin/curl`，那就是那个文件。

**CONNECT 隧道是什么**
Mihomo 帮 Claude Code 打通一条到目标服务器的管道，之后 Claude Code 直接在管道里发加密数据，Mihomo 只负责搬运不解密。日志里看到 `HTTP/1.1 200 Connection established` 就是隧道建立成功。

**规则引擎和策略组的区别**
- 规则引擎：判断"要不要走代理"（分拣员）
- 策略组：判断"走哪个节点"（选快递公司）

**扬帆云是软件还是账号**
扬帆云是机场（订阅服务），提供节点列表。Mihomo 是软件，拿着扬帆云的节点列表干活。就像快递员（Mihomo）用你的会员卡（扬帆云）寄快递。

**为什么美国节点 Windows 能用但服务器不能用**
Windows 本机走的是你家/宿舍网络出口，服务器走的是校园网出口（219.231.133.120），GFW 对不同出口的封锁程度不同，校园网出口访问美国节点会被 reset。

**一个程序可以开几个端口**
可以开多个。Mihomo 开了两个：7892（接收代理请求）和 9091（接收管理命令）。

## 一、Mihomo 启动（服务器重启后第一步）

Mihomo 不会自动启动，需要手动执行：

```bash
# 第一步：启动
nohup /home/PuMengYu/bin/mihomo \
  -f /home/PuMengYu/.config/clash/yangfan.yaml \
  -d /home/PuMengYu/.config/clash/ \
  > /tmp/clash.log 2>&1 &
sleep 2 && tail /tmp/clash.log
# 看到 "Mixed(http+socks) proxy listening at: [::]:7892" 即成功

# 第二步：切到法国节点
curl --noproxy '*' -X PUT http://127.0.0.1:9091/proxies/%E6%89%AC%E5%B8%86%E4%BA%91 \
  -H "Content-Type: application/json" \
  -d '{"name": "level1-法国01"}'

# 第三步：验证
curl -v --proxy http://127.0.0.1:7892 https://api.anthropic.com 2>&1 | grep -E "SSL|error"
# 看到 "SSL connection using TLSv1.3" 即正常
```

### 开终端自动启动（加到 ~/.bashrc）

```bash
if ! pgrep -x "mihomo" > /dev/null 2>&1; then
    nohup /home/PuMengYu/bin/mihomo \
        -f /home/PuMengYu/.config/clash/yangfan.yaml \
        -d /home/PuMengYu/.config/clash/ \
        > /tmp/clash.log 2>&1 &
fi
```

## 三、快速诊断流程

```bash
# 步骤1：Mihomo 是否在跑？
ps aux | grep mihomo | grep -v grep

# 步骤2：端口是否监听？
ss -tlnp | grep 7892

# 步骤3：代理能通外网吗？
curl --proxy http://127.0.0.1:7892 --max-time 10 https://api.anthropic.com \
  -o /dev/null -w "%{http_code}" -s
# 200 或 301 即正常

# 步骤4：看当前节点
curl --noproxy '*' -s http://127.0.0.1:9091/proxies | python3 -c "
import json,sys
d=json.load(sys.stdin)
for name,info in d['proxies'].items():
    if info.get('type')=='Selector':
        print(name,'->', info.get('now'))
"
```

| 步骤1/2 | 步骤3 | 结论 |
|---------|-------|------|
| 正常 | 200/301 | 代理正常，问题在别处 |
| 正常 | 非200 | 节点挂了，切换节点 |
| 无输出 | - | Mihomo 没在跑，回到第一节启动 |

## 七、常见坑

**访问 9091 返回空或 JSON 报错**
原因：curl 读了 `http_proxy` 环境变量，把请求转发出去了。
解决：必须加 `--noproxy '*'`。

**端口 7891 被占**
ZhaoPu 的 clash（pid 2070）占用，无权 pkill。本用户固定用 7892，不要改回。

**启动报 vless / anytls 不支持**
用的版本不对，必须用 v1.19.13，路径 `/home/PuMengYu/bin/mihomo`。

**启动报 Can't find MMDB**
服务器访问 GitHub 被 reset，无法自动下载 geoip.metadb。
启动时必须加 `-d /home/PuMengYu/.config/clash/`，文件已手动放在那里。

**端口配置 mixed-port 写的是哪里的地址**
是 Mihomo 在本机监听的端口号，不是扬帆云的地址。扬帆云节点地址写在 yaml 的 proxies 列表里（远端服务器）。两者是不同层的东西。
