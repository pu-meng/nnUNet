## 1. 图 1 中的 MedNeXt Bottleneck ×8 是什么，做什么

图 1 中的 `MedNeXt Bottleneck ×8` 表示：在 U 形网络最底部，连续串联 8 个相同的 `MedNeXtBlock`。

这里的“×8”不是 8 次下采样，也不是 8 个 MLA 模块。输入特征进入这 8 个 block 以后，空间尺寸和通道数始终保持为：

`[B,512,8,8,8]`

每一个 `MedNeXtBlock` 内部依次执行：

1. `3×3×3` depthwise convolution，提取局部三维空间特征；
2. GroupNorm；
3. `1×1×1` convolution，将通道从 `512` 扩展到 `4096`；
4. GELU；
5. `1×1×1` convolution，将通道从 `4096` 压缩回 `512`；
6. 与 block 的原始输入进行残差相加。

因此，这 8 个 MedNeXtBlock 的作用是：在最低空间分辨率上继续进行较深的局部三维特征提取，形成具有较强语义信息的 512 通道特征，然后再送入后面的 `MLA+MoE ×2` 进行全局位置之间的信息交互。

实际前向顺序是：

`MedNeXt Bottleneck ×8 → MLA+MoE Block ×2 → Decoder`

之所以是 8 个，是因为本文沿用了 MedNeXt-L 的固定深度配置：

`block_counts=[3,4,8,8,8,8,8,4,3]`

其中位于数组中间的第 5 个数字 `8`，就是 MedNeXt bottleneck 中的 block 数量。它属于原始 MedNeXt-L 主干配置，不是本文新增的 MLA 层数。

简短回答：

> 图 1 最底部的 `MedNeXt Bottleneck ×8` 是原始 MedNeXt-L 主干的一部分，表示在 `[B,512,8,8,8]` 的最低分辨率特征上连续执行 8 个 MedNeXtBlock。它们负责进一步提取局部三维语义特征，不改变特征尺寸；完成后才进入本文增加的两个 MLA+MoE block，补充全局上下文。

## 2. 图 1 中的 Stem Conv 是什么

Stem Conv 是网络接收原始 CT 后执行的第一层卷积。在本文代码中，它是：

`Conv3d(1,32,kernel_size=1,stride=1)`

输入和输出形状为：

`[B,1,D,H,W] → [B,32,D,H,W]`

它的作用是将单通道 CT 强度映射成 32 通道的初始特征，供后面的 MedNeXt encoder 使用。

因为卷积核为 `1×1×1`、stride 为 1，所以 Stem Conv：

- 不进行下采样；
- 不改变 `D、H、W`；
- 主要完成从原始 CT 到网络特征空间的通道映射。

因此，它更准确的含义是“输入特征投影层”，不是一个复杂的特征提取 stage。

简短回答：

> Stem Conv 是网络的输入投影层，用一个 `1×1×1` 三维卷积把单通道 CT 映射为 32 通道特征，空间尺寸保持不变，然后再交给 MedNeXt encoder。

## 3. 图 2 的 Encoder 和 Decoder 是否都使用 MedNeXt

是。本文的 Encoder 和 Decoder 都使用 MedNeXt 结构，并不是只有 Encoder 使用 MedNeXt。

### 图 2(a)：MedNeXt Encoder

Encoder 各 stage 使用多个 `MedNeXtBlock` 提取特征，并通过 `MedNeXtDownBlock` 完成下采样和通道增加。

整体变化为：

`32通道 → 64通道 → 128通道 → 256通道 → 512通道`

空间尺寸逐级变为：

`128³ → 64³ → 32³ → 16³ → 8³`

Encoder 各分辨率的输出还会作为 skip feature 送到 Decoder。

### 图 2(b)：单个 MedNeXtBlock

图 2(b) 展开的不是一个额外网络，而是 Encoder、MedNeXt bottleneck 和 Decoder stage 中反复使用的基本 MedNeXtBlock。

它的基本流程是：

`Depthwise Conv → GroupNorm → 通道扩展 → GELU → 通道压缩 → 残差相加`

图中以 bottleneck 的 512 通道 block 为例，所以显示：

`512 → 4096 → 512`

### 图 2(c)：MedNeXt Decoder

Decoder 同样使用 MedNeXt。每一级的真实顺序是：

1. `MedNeXtUpBlock` 对低分辨率特征进行上采样并减少通道数；
2. 与 Encoder 传来的同分辨率 skip feature 逐元素相加；
3. 再经过多个 `MedNeXtBlock` 进行特征恢复和融合。

最后通过 `1×1×1` segmentation head 输出背景、肝脏和肿瘤三类预测。

简短回答：

> 本文 Encoder 和 Decoder 都沿用 MedNeXt-L。Encoder 使用 MedNeXtBlock 和 MedNeXtDownBlock逐级编码；Decoder使用MedNeXtUpBlock上采样，与Encoder的skip feature相加后，再经过MedNeXtBlock恢复特征。本文新增的结构只位于原始MedNeXt bottleneck之后、Decoder之前。

## 4. 为什么说 ConvNeXt 和 MedNeXt 借鉴了 Transformer 的现代化设计

Transformer 的特点不只是使用 self-attention，还在于它把两类计算相对明确地分开：

1. self-attention 主要负责不同空间位置，也就是不同 token 之间的信息交互；
2. FFN 对每个 token 分别进行特征维度变换，主要负责通道信息的混合。

这种结构可以概括为：

`空间/token混合 → 通道混合`

ConvNeXt 借鉴了这种分工方式，但仍然是卷积网络：

1. depthwise convolution 在每个通道内独立进行空间卷积，主要负责空间信息混合；
2. `1×1` convolution 负责不同通道之间的信息混合，并完成通道扩展和压缩；
3. residual connection 保留输入信息并稳定深层训练。

MedNeXt 将这一设计扩展到三维医学图像。在本文的一个 `MedNeXtBlock` 中：

`3×3×3 Depthwise Conv → GroupNorm → 1×1×1通道扩展 → GELU → 1×1×1通道压缩 → 残差相加`

其中：

- `3×3×3 depthwise convolution` 负责三维空间信息混合；
- 两个 `1×1×1 convolution` 负责通道信息混合；
- 在 bottleneck 中，通道变化为 `512 → 4096 → 512`。

因此，更准确的说法是：

> ConvNeXt和MedNeXt借鉴了Transformer将空间/token混合与通道混合分工处理的现代化模块设计。不同之处在于，Transformer主要使用self-attention进行全局token交互，而ConvNeXt和MedNeXt使用depthwise convolution进行局部空间混合。

还需要注意，不能把这种“分离”说成完全没有交叉。Transformer的Q、K、V线性投影也会变换特征维度；这里强调的是两个子模块的主要职责不同，而不是数学上绝对隔离。

简短回答：

> Transformer的优势不只来自self-attention，它还把token之间的空间交互和token内部的通道变换分成attention与FFN两个部分。ConvNeXt借鉴了这种设计，用depthwise convolution负责空间混合，用`1×1`卷积负责通道混合；MedNeXt再把它扩展到三维医学图像。区别是Transformer的self-attention可以直接建立全局位置关系，而MedNeXt的depthwise convolution仍然主要进行局部空间建模。

## 5. 自然语言和三维图像分别怎样进入 Transformer

为了避免符号混淆，下面统一使用：

- `B`：batch size；
- `L`：自然语言序列长度；
- `E`：每个 token 的特征维度，也叫 embedding dimension；
- `C`：三维图像特征的通道数；
- `Z、H、W`：三维图像的深度、高度和宽度；
- `N=Z×H×W`：三维特征展平后的空间 token 数；
- `h`：attention head 数；
- `d=E/h`：每个 head 的特征维度。

### 5.1 自然语言 Transformer

自然语言最开始通常是 token ID：

`Token IDs: [B,L]`

经过词嵌入和位置信息后，得到：

`X: [B,L,E]`

这里：

- `L` 个 token 对应一句话中的 `L` 个词或子词；
- 每个 token 使用一个 `E` 维向量表示。

以标准多头 self-attention 为例：

#### 第一步：生成 Q、K、V

对最后一个特征维度进行三个线性投影：

`Q=XW_Q: [B,L,E]`

`K=XW_K: [B,L,E]`

`V=XW_V: [B,L,E]`

#### 第二步：拆成多个 attention heads

`[B,L,E] → [B,h,L,d]`

其中 `d=E/h`。

#### 第三步：计算 token 与 token 的关系

`QKᵀ: [B,h,L,d] × [B,h,d,L] → [B,h,L,L]`

`[B,h,L,L]` 中的每个值表示：某个词应该关注另一个词多少。

经过 softmax 后与 V 相乘：

`Attention×V: [B,h,L,L] × [B,h,L,d] → [B,h,L,d]`

#### 第四步：合并多个 heads

`[B,h,L,d] → [B,L,E]`

然后经过输出投影和残差相加：

`X₁=X+Attention(LayerNorm(X)): [B,L,E]`

#### 第五步：FFN进行通道变换

FFN对每个词分别执行相同的线性层：

`[B,L,E] → [B,L,rE] → [B,L,E]`

FFN不在不同词之间交换信息，只变换每个词自己的特征维度。最终：

`X₂=X₁+FFN(LayerNorm(X₁)): [B,L,E]`

因此，自然语言Transformer中：

- self-attention沿`L`维混合不同词的信息；
- FFN沿`E`维变换每个词的特征。

### 5.2 普通三维图像 Transformer

原始三维图像或三维特征为：

`X_img: [B,C,Z,H,W]`

Transformer要求输入是token序列，所以首先要将图像变成：

`X_seq: [B,N,E]`

常见做法是先进行三维Patch Embedding：

`[B,C,Z,H,W] → [B,E,Z',H',W']`

然后展平空间维度并转置：

`[B,E,Z',H',W'] → [B,E,N] → [B,N,E]`

其中：

`N=Z'×H'×W'`

这时，每个三维patch或空间位置就是一个图像token，每个token由一个`E`维向量表示。

进入Transformer以后，计算与自然语言完全同构：

`Q、K、V: [B,N,E]`

`多头形式: [B,h,N,d]`

`注意力矩阵: [B,h,N,N]`

`注意力输出: [B,N,E]`

`FFN: [B,N,E] → [B,N,rE] → [B,N,E]`

区别只在token的含义：

| 自然语言 | 三维图像 |
|---|---|
| 一个token是一个词或子词 | 一个token是一个三维patch或空间位置 |
| 序列长度为`L` | 空间token数为`N=Z'×H'×W'` |
| attention学习词与词的关系 | attention学习空间位置与空间位置的关系 |
| FFN变换词的特征 | FFN变换空间位置的通道特征 |

Transformer输出仍为`[B,N,E]`。如果后面连接图像Decoder，需要反向变换：

`[B,N,E] → [B,E,N] → [B,E,Z',H',W']`

### 5.3 本文模型的实际 Transformer 操作

本文不是直接把原始CT切成patch送入Transformer。原始CT先经过MedNeXt Encoder和8个MedNeXt bottleneck blocks，得到：

`X: [B,512,8,8,8]`

然后执行：

`flatten(2): [B,512,8,8,8] → [B,512,512]`

第一个`512`是通道数，第二个`512=8×8×8`是空间位置数。

再执行：

`transpose(1,2): [B,C,N] → [B,N,C]`

因此进入MLA+MoE block的实际序列是：

`X_seq: [B,512,512]`

这里两个512数值相同，但含义不同：

- 第二维`N=512`：512个三维空间位置；
- 第三维`E=512`：每个空间位置的512维通道特征。

本文使用8个attention heads，所以：

`h=8`

`d=512/8=64`

MLA中的实际shape变化为：

`Q: [B,512,512] → [B,8,512,64]`

Key和Value先共享低秩表示：

`C_KV: [B,512,512] → [B,512,128]`

再分别生成：

`K: [B,512,128] → [B,8,512,64]`

`V: [B,512,128] → [B,8,512,64]`

计算全局空间注意力：

`QKᵀ: [B,8,512,64] × [B,8,64,512] → [B,8,512,512]`

这里的注意力矩阵表示：每个head中，512个三维空间位置两两之间的关系。

注意力矩阵与V相乘：

`[B,8,512,512] × [B,8,512,64] → [B,8,512,64]`

合并8个heads：

`[B,8,512,64] → [B,512,512]`

完成两次`MLA+MoE block`后，再恢复三维特征：

`[B,N,C] → [B,C,N] → [B,512,8,8,8]`

最后进入MedNeXt Decoder。

完整流程为：

`CT [B,1,128,128,128]`

`→ MedNeXt Encoder`

`→ MedNeXt Bottleneck ×8 [B,512,8,8,8]`

`→ Flatten+Transpose [B,512个位置,512维特征]`

`→ MLA+MoE ×2`

`→ Transpose+Reshape [B,512,8,8,8]`

`→ MedNeXt Decoder`

### 5.4 空间混合和通道混合具体发生在哪里

| 模块 | 输入 | 主要混合的维度 | 作用 |
|---|---|---|---|
| 自然语言self-attention | `[B,L,E]` | `L` | 不同词之间交换信息 |
| 图像self-attention | `[B,N,E]` | `N` | 不同空间位置之间交换信息 |
| Transformer FFN | `[B,N,E]` | `E` | 每个位置内部进行通道变换 |
| MedNeXt depthwise convolution | `[B,C,Z,H,W]` | `Z、H、W` | 每个通道独立进行局部空间混合 |
| MedNeXt `1×1×1` convolution | `[B,C,Z,H,W]` | `C` | 每个空间位置进行通道混合 |

### 5.5 当前实现中的位置信息

普通ViT通常加入绝对位置编码，Swin Transformer通常加入相对位置偏置。

本文当前`MLABottleneck3D`代码没有额外加入显式位置编码。MLA接收的是已经经过多层三维卷积的MedNeXt bottleneck特征，这些特征包含卷积提取的局部空间上下文；序列处理完成后，也会按照原来的展平顺序恢复成`8×8×8`三维布局。

但是从严格机制上说，当前attention模块本身没有单独编码每个token的绝对三维坐标。因此不能表述为“MLA显式学习了三维绝对位置”，更准确的说法是：

> MLA在卷积编码后的512个空间token之间执行全局内容交互，空间结构主要由前面的三维卷积特征和处理后的三维布局恢复共同保留。

简短回答：

> 自然语言先表示成`[B,L,E]`，其中`L`是词的数量；三维图像先将`[B,C,Z,H,W]`展平并转置成`[B,N,E]`，其中`N=Z×H×W`是空间位置数量。进入Transformer后，两者的计算完全同构：self-attention沿`L`或`N`维建立token之间的关系，FFN沿`E`维变换每个token的通道特征。本文的实际输入是`[B,512,8,8,8]`，转换成512个空间token、每个token 512维，再由8个attention heads计算`[B,8,512,512]`的全局空间关系矩阵。

## 6. 图 3(a) 原标题为什么叫 MLABottleneck3D Tensor Flow

图3(a)标题中的`Tensor Flow`是两个单词，表示“张量流动过程”，不是谷歌的深度学习框架`TensorFlow`。

这里的tensor是模型中传递的多维特征数组。例如：

`[B,512,8,8,8]`

这里的flow表示这个张量进入`MLABottleneck3D`以后，依次经过哪些操作、形状和维度排列怎样变化，以及最后输出到哪里。

图3(a)展示的是：

`MedNeXt bottleneck output`

`[B,512,8,8,8]`

`↓ Flatten + transpose`

`[B,512个空间位置,512维特征]`

`↓ MLA+MoE Block ×2`

`[B,512,512]`

`↓ Final LayerNorm`

`[B,512,512]`

`↓ Transpose + reshape`

`[B,512,8,8,8]`

因此，图3(a)叫`Tensor Flow`，是因为它重点回答：

> MedNeXt输出的五维三维特征张量，怎样转换成Transformer可以处理的三维token序列，又怎样恢复成Decoder需要的五维三维特征。

图3(a)不负责展开一个MLA+MoE block内部的计算。内部的两条残差路径由图3(b)说明；MLA内部的Q、K、V低秩投影由图4说明；MoE内部的专家选择和计算由图5说明。

需要注意，原英文标题容易让读者误认为`TensorFlow`框架。论文正文中的中文图注已经使用更准确的“MLABottleneck3D外层流程”。图内标题已从：

`(a) MLABottleneck3D Tensor Flow`

改为更明确的：

`(a) MLABottleneck3D Feature Transformation`

`Feature Transformation`表示特征形状和排列的转换过程，也不会与TensorFlow框架混淆。

简短回答：

> 图3(a)中的Tensor Flow是“张量变化流程”，不是TensorFlow框架。它展示`[B,512,8,8,8]`的三维特征怎样通过flatten和transpose变成`[B,512,512]`的token序列，经过两个MLA+MoE blocks后，再恢复为原来的三维特征形状。它只画MLABottleneck3D的外层输入输出流程，内部计算分别在后续子图中展开。

## 7. MedNeXt、nnU-Net、MLA和MoE代码来源核查

### 7.1 可直接说的结论

> 本文使用的MedNeXt网络核心来自MIC-DKFZ官方MedNeXt v1代码，MedNeXt-L结构参数也与官方Large配置一致；但整个实验系统不是把官方MedNeXt仓库原样运行，而是把官方MedNeXt-L网络接入本地nnU-Net v2训练和推理流水线，再在MedNeXt bottleneck后加入本文自行实现的简化MLA和MoE。MLA、MoE借鉴DeepSeek论文思想，不是DeepSeek官方代码，也不是完整复现。

### 7.2 实现细节

#### 7.2.1 各部分来源总表

| 部分 | 实际来源 | 是否为官方原代码 | 本文做了什么 |
|---|---|---|---|
| `MedNeXtBlock`、DownBlock、UpBlock | MIC-DKFZ官方MedNeXt仓库 | 是 | 直接import并使用 |
| MedNeXt Encoder、bottleneck、Decoder总体网络 | MIC-DKFZ官方`MedNextV1.py` | 核心是 | 使用官方MedNeXt-L结构和参数 |

#### 7.2.4 MLA是不是DeepSeek官方代码

不是。

本地MLA直接定义在：

`pumengyu/architectures/mla_unetr.py::MultiHeadLatentAttention`

代码没有import DeepSeek官方MLA类，而是使用PyTorch的`Linear`、`LayerNorm`和矩阵乘法自行实现。

本地MLA保留了[DeepSeek-V2](https://arxiv.org/abs/2405.04434)的一个核心思想：

> Key和Value先共享一个低秩潜变量，再分别上投影生成K和V。

但它与[DeepSeek-V2官方模型代码](https://huggingface.co/deepseek-ai/DeepSeek-V2/blob/main/modeling_deepseek.py)存在明显差异：

| DeepSeek-V2官方MLA | 本文简化MLA |
|---|---|
| 面向自回归语言生成和KV cache | 面向三维分割，没有跨步KV cache |
| Query也有低秩压缩和上投影 | Query直接`512→512` |
| 使用解耦RoPE处理位置信息 | 没有显式RoPE或三维位置编码 |
| 区分带位置和不带位置的Q/K部分 | 没有该拆分 |
| 面向因果attention | 对512个空间token执行非因果全局attention |
| 主要目标是降低推理KV cache | 主要减少K/V投影参数并施加低秩约束 |

而且本文仍显式生成完整的：

`[B,8,512,512]`

注意力矩阵，没有消除关于token数量的二次复杂度。

因此论文中应写：

> 本文借鉴DeepSeek-V2 MLA的低秩键值表示思想，设计适用于三维bottleneck特征的简化MLA-style注意力。

不能写：

> 本文直接使用或完整复现DeepSeek-V2官方MLA。

#### 7.2.5 MoE是不是DeepSeek官方代码

也不是。

本地MoE直接定义在：

`pumengyu/architectures/mla_unetr.py::MoEFFN`

它借鉴了两类思想：

1. [DeepSeekMoE/DeepSeek-V2](https://github.com/deepseek-ai/DeepSeek-V2)的shared experts与routed experts；
2. [DeepSeek-V3](https://arxiv.org/abs/2412.19437)中使用bias辅助负载均衡、避免直接加入辅助损失的思想。

本地实现为：

```text
1个shared expert
4个routed experts
每个token选择top-2 routed experts
每个expert执行512→1024→512
shared output + routed weighted output
```

与DeepSeek官方MoE的主要差异包括：

| DeepSeek官方MoE | 本文简化MoE |
|---|---|
| 面向大规模语言模型和大量专家 | 只有1个shared、4个routed experts |
| 使用官方模型配置和分布式expert parallel | 单机PyTorch模块，没有expert parallel |
| 专家通常使用门控MLP结构 | 本文使用`Linear→GELU→Linear` |
| 官方路由包含更完整的分组、缩放和训练机制 | 本文使用简单线性选择器和top-2 |
| 真正只调度被选中的专家以获得稀疏计算 | 本文先计算4个routed experts的全部输出，再gather top-2 |
| DeepSeek-V3负载均衡服务于大规模训练 | 本文使用本地EMA负载估计和bias更新简化实现 |

尤其需要注意：本文代码虽然在输出融合上只选择top-2，但为了实现简单，实际先计算了全部4个routed experts。因此它具有条件路由行为，却没有获得官方稀疏MoE“只计算被选专家”的完整计算节省。

准确表述是：

> 本文MoE-FFN借鉴DeepSeekMoE的shared/routed expert组织方式和DeepSeek-V3的无辅助损失负载均衡思想，并针对低分辨率三维token实现小规模简化版本。

不能写：

> 本文使用DeepSeek-V3官方MoE代码或完整复现DeepSeek-V3 MoE。

## 8. 汇报前先明确：读者、论点和创新贡献

### 8.1 可直接说的总论

> 这篇论文讲给了解医学图像分割基本方法、但不一定了解 MedNeXt、MLA 和 MoE 实现的老师或审稿人。我要证明的不是“加上 MLA 和 MoE 后所有数据集都更好”，而是：强 MedNeXt 局部卷积与最低分辨率全局上下文具有互补潜力，但内部高分不等于外部可靠，attention 与 FFN 的收益会随数据域变化。我的贡献是提出这一混合结构，并通过 MHA/MLA × MLP/MoE 控制变量实验、30 种 trainer 的三个数据域比较和失败病例分析，明确它在哪些场景有效、又有哪些边界。

### 8.2 实现细节与论证材料

#### 8.2.1 这篇论文讲给谁听

默认读者是医学图像分割或计算机视觉方向的老师和审稿人。他们知道 U-Net、CNN 和 Transformer 的基本概念，但不一定了解 MedNeXt、MLA、MoE，也不了解本仓库的 trainer 命名和代码。

4. 用什么受控实验验证；

简短回答：

> 我的读者是懂医学图像分割基本方法、但不了解 MedNeXt、MLA 和 MoE 具体实现的老师或审稿人。因此我要先讲问题和作用，再讲输入形状、真实模块、实验结果和证据边界。

#### 8.2.2 我要证明的核心论点

论文真正要证明的不是“我加了 MLA 和 MoE，所以所有数据集都更好”，而是下面这条完整论证：

> 内部测试集上的高 Dice 不能直接代表跨数据集可靠性；保留 MedNeXt 的强局部三维卷积主干，并只在最低分辨率 bottleneck 补充全局上下文，能够改善部分外部数据域，但 attention 与 FFN 的组合收益具有明显的数据域依赖性。

证据链分为三步：

1. MedNeXt、MHA、MLA、MHA+MoE、MLA+MoE 在统一训练配置下组成控制变量对照；
2. 同时在 MSD internal、3D-IRCADb 和 HCCReferencedCT v2 上评价，而不是只看单一内部数据集；
3. 结果显示三个数据域的第一名不同，因此不能把一个外部数据集上的提升写成统一泛化优势。

最短汇报版本：

> 我要证明的是：强局部卷积和低分辨率全局上下文具有互补潜力，但内部高分不等于外部可靠，模块收益还会随数据域变化。

#### 8.2.3 我的创新贡献是什么

1. **结构贡献：**保留完整 MedNeXt-L Encoder、卷积 bottleneck 和 Decoder，只在最低分辨率处加入简化 MLA-style attention 与 MoE-FFN，以较小主干改动补充全局上下文。
2. **实验贡献：**完成 MHA/MLA × MLP/MoE 的三域控制变量矩阵，区分 attention 路径、FFN 类型和数据域的交互影响。
3. **验证贡献：**建立 30 种 source-only trainer 的公平比较池，并在 MSD internal、3D-IRCADb 和 HCCReferencedCT v2 中分别排名，揭示内部排名与外部排名不一致。
4. **分析贡献：**结合无肿瘤误报、小病灶漏检、CT 视觉歧义和三维上下文错误分析模型局限，而不只报告平均 Dice。

这里必须主动说明证据边界：

- MLA 和 MoE 是借鉴 DeepSeek 思想的本地简化实现，不是官方代码的完整复现；
- 当前证据是固定 checkpoint 的三数据域比较，不是多随机种子稳定性结论；
- 论文没有证明 MLA 或 MoE 单独在所有数据域都有效；
- 论文也没有证明某个配置可以“三域通吃”。

简短回答：

> 我的贡献不只是加模块，而是提出一个“强 MedNeXt 局部主干加低分辨率全局上下文”的混合结构，并用严格的 attention–FFN 控制变量实验和三个数据域验证它的有效范围。结果既给出 IRCADb 上的正向证据，也明确展示 HCC 上的域依赖和失败边界。

## 9. 模型效率与实际训练成本

### 9.1 为什么不能只报参数量

| 指标 | 本文中回答的问题 | 使用边界 |
|---|---|---|
| Params | 模型权重规模和存储成本 | 不代表真实速度，也不等于运行显存 |
| FLOPs | 固定输入下的理论计算量 | 只覆盖计数器支持的运算，不代表真实速度 |
| Peak Memory | 固定运行协议下的硬件显存需求 | 必须区分推理峰值和训练峰值，并记录实现与输入 |
| Latency | batch=1 时单个 patch 的真实前向时间 | 依赖 GPU、AMP、compile、warm-up 和系统负载 |
| Throughput | 单位时间处理的样本或 patch 数 | 强依赖 batch；当前不单独汇报推理吞吐 |
| Training time | 完成训练所需的真实 wall-clock 成本 | 必须同时写 GPU 数、compile、epoch/step 数和中断情况 |

因此，参数量小只能说明模型文件和权重容量小，不能直接推出 FLOPs 小、显存低或运行快。效率结论必须把理论量、单次实测和完整训练成本分开汇报。

### 9.2 统一单 Patch 前向 Benchmark

以下六个结构在同一张 RTX 4090 D、同一 PyTorch/CUDA 环境下测量。输入固定为 `1×1×128×128×128`，deep supervision 关闭，AMP FP16，`torch.compile` 关闭；先 warm-up 10 次，再重复 30 次。峰值显存是单 patch 前向的 CUDA allocated memory，不是训练峰值显存，也不包含预处理、滑窗拼接和 NIfTI I/O。

| 方法 | Params | FLOPs | 单 Patch Latency | 推理 Peak Memory |
|---|---:|---:|---:|---:|
| EfficientMedNeXt-L | **2.194 M** | **242.20 G** | 157.49 ± 0.10 ms | 2.41 GiB |
| MedNeXt | 61.782 M | 989.22 G | **96.51 ± 0.09 ms** | **2.37 GiB** |
| MedNeXt_MLA | 67.429 M | 996.06 G | 96.85 ± 0.07 ms | 2.41 GiB |
| MedNeXt_MHA | 68.084 M | 996.73 G | 96.76 ± 0.08 ms | 2.42 GiB |
| MedNeXt_MLA_MoE | 73.735 M | 1002.51 G | 97.19 ± 0.08 ms | 2.45 GiB |
| MedNeXt_MHA_MoE | 74.390 M | 1003.18 G | 97.18 ± 0.08 ms | 2.45 GiB |

这张表最重要的现象是：EfficientMedNeXt-L 的参数量和 FLOPs 最低，但当前官方实现的真实单 patch 前向反而最慢。它证明 Params、FLOPs 和真实速度不能互相替代。MLA/MHA/MoE 四个变体相对 MedNeXt 增加了参数和理论计算，但在该固定前向协议下的延迟差异小于 1 ms；这不等于它们的完整病例推理或训练成本相同。

当前不额外列推理 Throughput：这里 batch 固定为 1，`patch/s` 只是 Latency 的倒数，不能提供独立结论。以后如果比较上线吞吐，应固定 batch、滑窗参数和病例清单，另做端到端测试。
