# 研究问题来源与论文分类：我对“论文问题从哪里来”的理解

> 说明：这不是严格的学术分类，而是我为了理解“研究问题如何被构造、创新如何产生”建立的工作分类。不同论文可能同时属于两类甚至三类，分类重点在于**研究的起点**。

---

## 1. 我目前最核心的三类

### 第一类：从具体 Failure / Task / Data Problem 出发

核心逻辑：

```text
Baseline → 稳定失败现象 → 原因假设 → 针对性方法 → 定向验证
```

典型问题：

- 小目标、小病灶容易漏检；
- 模糊边界处理不好；
- 某些困难样本性能明显下降；
- 跨数据集、跨中心性能下降；
- 类别不平衡、噪声标注、长尾问题；
- 某种特定情况下 precision / recall 明显失衡。

这类研究的重点不是先想“我要加什么模块”，而是先问：

> 模型究竟在哪里稳定失败？为什么会失败？

然后再让方法和这个失败现象直接对应。

例如：

```text
小病灶 recall 低
→ 怀疑深层下采样后细节丢失 / 大目标语义占优
→ 设计 detail-context adaptive fusion
→ 用 size-stratified Dice / Recall / lesion-wise 指标验证
```

这类问题最适合我当前直接入手，因为问题可以从已有 baseline 和实际 case 中获得。在各个级别的期刊这类论文占比少,就算是3区/4区也是占比很少,但是直觉上跟适合我入门;

---

### 第二类：从现有 Method / System Limitation 出发

核心逻辑：

```text
现有方法 → 找到结构或系统限制 → 设计新的机制 / pipeline → benchmark + ablation 验证
```

典型问题：

- CNN 局部建模强，但全局依赖不足；
- 多尺度信息融合不足；
- encoder / decoder feature 存在 semantic gap；
- 多模态之间对齐不足；
- feature fusion 太粗糙；
- Transformer 在高分辨率 / 3D 上计算复杂度太高；
- 一个方法需要大量人工调参或专家经验；
- 模型 scaling 规律不清楚。

这一类不一定先从具体失败病例开始，而是直接研究：

> 现有方法的设计本身哪里不够好？

然后围绕这个 limitation 设计结构。

---

### 第三类：从 Field / Paradigm 的默认假设出发

核心逻辑：

```text
领域长期默认做法 → 质疑“为什么必须这样？” → 新范式 / 新任务定义 / 新基础框架
```

典型问题：

- 序列建模是否必须依赖 recurrence？
- 视觉是否必须依赖 CNN？
- segmentation 是否必须一个任务训练一个专用模型？
- 医学分割是否必须依赖专家手工配置整个训练 pipeline？

这类通常抽象层次最高，也更容易产生 landmark 工作，但对于当前阶段不一定最适合直接作为切入点。

---

## 2. 还可以补充的两类

前三类已经覆盖大多数“方法论文”的研究起点，但为了更完整，我认为还可以增加两类辅助分类。

### 第四类：从 Data / Annotation / Evaluation Protocol 本身出发

这类不一定主要改网络，而是发现：

> 问题可能不只在模型，而在数据定义、标注规则、训练协议或评价方式。

例如：

- 不同数据集标注 ontology 不一致；
- 多标注者之间存在 ambiguity；
- Dice 很高但 lesion-wise recall 很差；
- 单一内部测试集不能说明 external reliability；
- 训练集 / 测试集存在 domain shift；
- benchmark protocol 本身不足以回答真实问题。

逻辑：

```text
现有数据 / 标注 / 评价协议
→ 发现其不能正确描述问题
→ 重新定义 protocol / metric / dataset organization
→ 得到新的结论或方法
```

这一类和第一类有交叉，但重点不同：第一类重点是“模型在哪失败”，第四类重点是“我们现在描述问题的方法是否就有缺陷”。

---

### 第五类：从 Efficiency / Deployment / Engineering Constraint 出发

核心问题：

> 方法不是不能做，而是太慢、太大、太贵、太难部署。

例如：

- 3D 模型显存占用太高；
- Transformer 计算复杂度过高；
- inference 太慢；
- 多模型 ensemble 成本太高；
- 医院 / 边缘设备无法承受大模型；
- 训练 pipeline 太复杂、难复现。

逻辑：

```text
现有方法有效但成本太高
→ 找主要计算 / 内存瓶颈
→ 设计轻量化 / 更高效机制
→ 在性能-成本 trade-off 上验证
```

这一类本质上仍属于 method/system-driven，但单独拿出来很实用，因为工程型论文中非常常见。

# 3. 几个典型论文 / 方法放到这个框架里

| 论文 / 方法 | 它抓的核心问题 | 主要类型 | 问题主题是怎么构造出来的 |
|---|---|---|---|
| **U-Net** | 医学标注少，但 dense prediction 又需要精确定位 | Task/Data + Method | 从“小数据 + 定位需求”构造 U-shaped encoder-decoder 与 skip connection |
| **nnU-Net** | 每个医学分割任务都依赖专家手工配置 preprocessing、spacing、patch、network、training、postprocessing | **Method / System-driven** | 不把创新点放在新 backbone，而是把“人工调 pipeline”本身定义成系统问题，并自动适配数据集 |
| **Transformer** | 序列建模是否一定需要 recurrence / convolution | **Field / Paradigm-driven** | 直接质疑领域默认结构，提出纯 attention 范式 |
| **ViT** | 视觉任务是否一定必须依赖 CNN | **Field / Paradigm-driven** | 将 Transformer 直接用于 image patches，挑战 CNN 默认地位 |
| **Swin Transformer** | 全局 self-attention 在高分辨率视觉中太贵，而且缺少层次化、多尺度表示 | Method + Paradigm | 接受 Transformer 大方向，但针对 dense vision 的实际 limitation 做 window + hierarchy |
| **ConvNeXt** | Transformer 的优势到底来自 attention，还是来自现代设计与训练 recipe？纯 CNN 是否仍有潜力 | **Field / Paradigm-driven** | 反过来重新审视 CNN，吸收现代架构设计原则 |
| **UNETR** | 3D segmentation 中 CNN 的长距离关系建模有限 | **Method-driven** | 从 encoder 的局部感受野 limitation 出发，用 Transformer encoder 建模 global dependency |
| **Swin UNETR** | 3D 全局 Transformer 计算昂贵，同时医学数据有限 | **Method / System-driven** | hierarchical/window attention + 3D self-supervised representation |
| **MedNeXt** | ConvNeXt 式现代卷积设计能否真正适配 3D 医学分割，并形成可扩展的 ConvNet | **Method / Architecture-driven** | 从“现代 ConvNet + 3D 医学任务约束 + scaling”构造问题，而不是从单个 failure case 出发 |
| **SAM** | segmentation 是否必须是固定类别、固定数据集、固定模型 | **Field / Paradigm-driven** | 重新定义 segmentation 为 promptable task，并配套通用模型与 data engine |
| **MedSAM** | 医学分割长期是一个器官 / 模态 / 疾病对应一个 specialist model，能否形成通用医学分割模型 | **Field / Paradigm-driven** | 将 promptable general segmentation 范式迁移到医学领域 |
| **MSA-Net** | 多尺度信息、边缘定位和 high / low-level feature fusion 不充分 | **Method-driven** | 从结构 limitation 出发，设计 MPAB、FFB，并组合 ASPP、Strip Conv 等已有模块 |
| **Failure analysis 类论文 / 我的下一步方向** | small lesion、模糊边界、跨数据集下降、误报等稳定 failure | **Failure / Task / Data-driven** | 先跑 baseline，再从 case / subgroup 中找稳定问题，再设计针对性机制 |

# 4. nnU-Net 和 MedNeXt 为什么很适合说明“问题主题是通用的”

## nnU-Net：问题不在“网络不够新”，而在“训练系统太依赖人工配置”

它抓的问题不是：

```text
U-Net 的某个卷积块不好
```

而是：

```text
不同数据集
→ spacing、patch、batch、network topology、training、postprocessing 都不同
→ 过去依赖专家经验
→ 难复现、难迁移、难公平比较
```

因此它把“专家调参”本身变成一个可以系统化解决的问题：

```text
Dataset fingerprint
→ 自动配置 pipeline
→ 形成 self-configuring segmentation framework
```

所以它是一个非常典型的 **System Problem**。

这个思路并不局限于医学图像：

> 任何一个 AI 领域，只要一个系统严重依赖人工经验、手工配置、重复调参，都可以把“如何自动适配”本身定义成研究问题。

---

## MedNeXt：问题不在具体病例，而在“3D 医学 ConvNet 应该怎样现代化”

它的思路更接近：

```text
Transformer / ConvNeXt 时代出现新的网络设计经验
→ 这些原则能否迁移到 3D medical segmentation？
→ 3D ConvNet 应该怎样设计 block、kernel、scaling？
```

所以它解决的是一个更普遍的 architecture design problem：

> 不是“某个肿瘤为什么漏掉”，而是“一个更现代、更可扩展的 3D ConvNet 应该长什么样”。

这个思路同样可以迁移到其他领域，例如多模态：

```text
现有多模态融合方式是否过早 / 过晚？
不同模态应该在哪里交互？
模型 scaling 后性能如何变化？
跨模态 feature 是否存在冗余或冲突？
```

# 5. 三个层次其实可以理解成“问题抽象程度”不同

```text
Level 1：这个模型具体在哪里失败？
        ↓
Failure / Task / Data

Level 2：这个方法本身哪里设计得不够好？
        ↓
Method / System Limitation

Level 3：这个领域为什么一定要这样做？
        ↓
Field / Paradigm
```

第四、第五类则可以视为补充维度：

```text
Data / Annotation / Evaluation：我们描述问题的方式是否就有问题？
Efficiency / Deployment：这个方法能不能真正以合理成本工作？
```

# 6. 我目前准备采用的研究路线

我现在不准备一上来做第三类大问题，而是：

```text
第一类找问题
    +
第二类做方法
```

即：

```text
Baseline
→ 系统看 failure cases / subgroup metrics
→ 找一个稳定、范围小、可以复现的问题
→ 提出原因假设
→ 针对这个问题设计一个核心机制
→ overall + targeted metric + ablation + external validation
```

可以进一步压缩成：

```text
Failure 发现问题
→ Method 解决问题
→ Evidence 证明问题被解决
```

# 7. 我以前和现在的思路变化

以前更像：

```text
看到一个模块
→ 加进现有模型
→ 看指标涨不涨
→ 再解释 motivation
```

现在希望变成：

```text
先找稳定问题
→ 分析为什么失败
→ 再决定需要什么机制
→ 用针对性的证据验证
```

我目前最大的变化不是已经得到新的模型结果，而是开始建立：

> **“问题从哪里来 → 方法为什么这样设计 → 实验应该验证什么”**

这一整套研究逻辑。
